# 图片分镜的交付前审查

在 image-only 方案初稿完成后执行。读取原始请求、SRT、实际选定配置和已生成分镜，直接修订同一个 STORYBOARD.md。结构校验通过只证明字段和部分交接约束符合要求，不证明画面能看懂或提示词正确。

## 先确定本项目的连续性

按内容选择连续主角、多角色或无人物，不强制所有视频只有一个人物。连续主角或重复出现的角色，在 style.description 中写清稳定的外貌、发型、服装和需要连续的环境；多角色说明各自身份及出现原因。人物稳定特征进入相关主提示词与备用提示词，不能用“中老年人”等宽泛受众标签代替人物设定。

备用方案可以简化构图、改变视角或更换可用物件，但保留该镜的表达目标、角色身份、有效画风、图内文字和安全区约束。没有实际备用需求时 fallbackPrompt=null，不机械为每镜再造一个不同人物的故事。

## 检查最终交付，而不只检查策划说明

| 审查对象 | 判断依据 | 修订方式 |
|---|---|---|
| 观众可见文字 | 逐项读 inImageText、overlay.title/keywords/labels，并对照可读表。文字是否帮助观众理解本段，还是在描述编导工作？ | 内部叙事功能留在 narrativeBeat，删除误入屏幕字段的策划标签；真正讲解编导术语的内容仍可展示这些词，不做词语黑名单。 |
| 人物与世界连续性 | 相邻镜头、重复角色及其备用提示词是否符合项目人物设定？物件位置、姿态和空间关系是否自然？ | 修复无叙事理由的换人、换服装、环境跳变和不合理摆放；有意切换的角色/场景保留并说明作用。 |
| 一个静态瞬间 | 单张图片能否同时呈现描述的状态？是否把逐渐改变、先后完成、移动路径当成必须生成的过程？ | 选取可画的瞬间或有意义的静态对比；后期能实现的变化写入 usage，确需多个阶段则结合时间拆镜。不要把整个动作过程塞进一个生图请求。 |
| 信息负担 | 在该镜实际时长、画幅和字幕占用下，观众能否先注意到主要关系？ | 删除不帮助表达的装饰和重复隐喻；优先简化，再考虑合法切点。不得仅因减少物件就删除必要证据，也不设所有题材通用的物件数量上限。 |
| 画面传达的判断 | 忽略提示词里的免责声明，仅看拟呈现的并置、箭头、前后对比、表情与光效，会暗示什么事实或因果？ | 有证据才作相应表达；未支持的判断用中性场景/待核验项处理。提示词写“不表示因果”不能抵消画面实际暗示的因果。 |
| 画风与编排 | 主/备用提示词是否落实项目有效媒介、配色、人物和文字策略？裁切、推近和叠字是否侵入主体或字幕区？ | 对照配置快照修复漂移；合理的项目覆盖写明依据。把精确文字、来源与字幕安排在互不冲突的位置。 |

以上审查依据适用于健康、研报及其他图片题材。某一镜的具体改法不能自动升级为全局规则，例如不能因为一次隐喻过密就禁止隐喻、因为一次换人失误就禁止多人物。

## 跨字段修订与复查

把一镜当作完整设计来修订。先明确该镜最终要呈现的状态，再逐项核对 `visualIntent → image.assetNeed → prompt/fallbackPrompt或designBrief → inImageText/overlay → usage`，以及可读分镜表。字段用途不同，无需逐字相同；主体身份、物件位置、静态状态、有效画风和观众文字不能互相矛盾。narrativeBeat 可保留内部功能说明，不能因此复制到上屏字段。

例如，把动态过程改为静态结果后，素材需求里也不应仍要求生成该过程；移走不合理位置的物件后，构图、提示词和裁切要求应一致；删去内部上屏标签后，应同时检查 overlay 的三个子字段及可读表。有效的后期运动仍可保留，但须明确由已有静态素材如何实现，不能靠一张扁平图独立移动其中的物体。无需为了显得改动全面而修改正确的时间轴或无关字段。

按下面的顺序完成本轮交付：

1. 写完初稿后，从磁盘实际文件提取字段：`python3 scripts/image_timeline.py review STORYBOARD.md`。长片可用重复的 `--shot shot-001 --shot shot-002` 分批查看，覆盖所有镜头后再得出全片结论。该命令只提取 JSON 原值，不读取或采信文件里的“已审查”声明，也不会自动判语义通过。
2. 对照原始请求、SRT 和配置，检查提取结果中的屏幕文字、场景关系与上述字段链。对发现的问题记录镜头 ID、实际字段路径、问题内容和修订决定；问题记录放在同一文件说明部分，保持简短，不能写进 overlay。
3. 将决定落实到所有受影响字段及可读表，保存文件。修订后重新运行 review，核对问题位置的当前原值与关联字段；不能用计划怎么改、编辑前的输出或前一次审查说明代替复查。
4. 对保存后的最终版本运行带原始预设参数的 validate，检查可读表与 JSON 一致，再写本轮审查结论。若之后又改变设计，复查受影响字段；未解决问题保留 planned 和具体 openQuestions。

审查记录采用简短的“镜头/字段 — 原问题 — 当前修正 — 复查结果”，只记录实际发生的修订。没有发现问题时，说明实际检查过的镜头范围和字段，不能编造修正记录。若结论说某标签已删除而最终 overlay 仍含该标签，以实际字段为准，撤销通过结论并继续修订。修复后仍无法一致表达的部分报告为未完成，不用更长的正面说明掩盖。

用户提供上一版失败结果时，将其作为回归输入，逐项核对已知问题是否在最终字段中消失；同时检查改动是否破坏相邻镜头与全局约定。只在出现新的可重复问题时调整通用规则，不把当前文案的镜头、人物或具体措辞写成全局模板。

## 修订与交接状态

在当前授权范围内直接修复能确定的问题，然后重新校验。只有缺失的用户信息会影响关键选择时才列 openQuestions；不要为了完成审查而额外增加用户审批。未修复的配置、连续性或表达冲突保持 planned，不标 ready。

在同一个 STORYBOARD.md 的说明部分简要记录有实质影响的修订及镜头 ID；确无修订时写明实际检查范围。不要只写“六项全部通过”，不要另建第二份视觉计划或把审查说明写进 overlay。

交付时区分：脚本已检查的结构/时间/声明配置、基于文字方案完成的语义审查、尚未执行的图片效果和音画同步验证。一次执行成功不证明之后所有题材都不会再犯错。
